# Phase 0 코어 루프 설계 — v0.1

룬 없이 **추출 → 소환 → 전투 → 분해** 한 바퀴가 재미있는지 확인하는 단계. 이 루프가 재미없으면 룬 시스템은 무의미하므로, 모든 설계는 "최소한으로 구현해서 빨리 느낌을 본다"를 우선한다.

> 표기: **[확정]** 이 설계의 결정 / **[가정]** 플레이 테스트로 조정할 초기 수치 / **[확인 필요]** MSW 기능 존재 여부를 메이커에서 확인해야 함 (`AGENTS.md` 미확인 항목과 연결)

## 1. 목표와 성공 기준

| 항목 | 내용 |
| --- | --- |
| 목표 | 5~10분 플레이로 "내 그림자가 점점 쌓이고 강해지는 맛"이 있는지 확인 |
| 포함 | 그림자 추출, 보관(무제한), 소환(배치 한도 5), 전투, 분해 → 그림자 정수 |
| 제외 | 룬, 룬워드, 소켓, 승급 제단, 정예 승격, PvP, 파티, 장비 |
| 성공 기준 | ① 추출 성공 때 쾌감이 있다 ② "누구를 데리고 나갈지" 고민이 생긴다 ③ 분해가 아깝지 않고 쓸 곳이 보인다 ④ 소환수 5마리를 굴려도 서버가 멀쩡하다 |
| 실패 신호 | 소환수가 알아서 다 해서 할 일이 없다 / 추출이 지루한 확률 게임이다 / 약한 그림자가 그냥 쓰레기다 |

## 2. 코어 루프

```
적 처치 ──► 추출 판정 ──► 그림자 획득 ──► 보관함 (무제한)
   ▲                                        │
   │                                        ▼
   │                             배치 슬롯 5개에 소환
   │                                        │
   └────────── 전투 ◄───────────────────────┘
                 │
                 ├─► 그림자 사망 ──► 재소환 대기 후 다시 소환 가능
                 └─► 약한 그림자 ──► 분해 ──► 그림자 정수 ──► (Phase 2에서 룬 승급 재료)
```

Phase 0에서 그림자 정수는 **쓰는 곳이 없다.** 대신 "그림자 강화"(정수로 보관 중인 그림자 레벨업)를 임시 소비처로 둔다. 이 소비처가 없으면 분해 동기를 검증할 수 없다. **[확정]**

## 3. 스킬 (플레이어)

| 스킬 | 동작 | 비고 |
| --- | --- | --- |
| 그림자 추출 | 적 처치 시 자동 판정 (플레이어 입력 없음) | 실패하면 시체 소멸. 확률은 4장 |
| 그림자 소환 | 보관함에서 선택해 슬롯에 소환 | 슬롯 5개, 쿨다운 없음, 재소환 대기는 개체별 |
| 그림자 회수 | 소환 중인 그림자를 보관함으로 되돌림 | 즉시 가능 |
| 집결 | 모든 소환수가 플레이어 곁으로 이동 | 단축키 하나 **[가정]** |
| 그림자 분해 | 보관 중인 그림자를 정수로 변환 | 보관함 UI에서 선택 |
| 그림자 강화 | 정수를 소모해 그림자 레벨 +1 | Phase 0 임시 소비처 |

핵심 질문: 소환수에게 **직접 명령**을 줄 수 있어야 재미가 있는가? Phase 0에서는 자동 전투(가까운 적 추적·공격) + 집결만 구현해 보고, 지시 스킬은 느낌을 본 뒤 결정한다.

## 4. 데이터 구조

모든 데이터는 서버 권위. 클라이언트는 표시용 사본만 받는다.

### ShadowData (그림자 한 마리)

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `id` | string | 고유 ID (서버 발급) |
| `sourceId` | string | 원본 몬스터 종류 ID |
| `grade` | number | 1 일반 / 2 정예 후보 / 3 보스급 (Phase 0은 1~2만) **[가정]** |
| `level` | number | 그림자 레벨 (강화로 상승) |
| `hp`, `atk`, `def`, `moveSpeed` | number | 원본 스탯 × 계수 + 레벨 보정 |
| `deployed` | boolean | 소환 중 여부 |
| `respawnReadyAt` | number | 재소환 가능 시각 (서버 시간) |

### 추출 확률 **[가정]**

| 원본 등급 | 기본 추출 확률 | 그림자 등급 |
| --- | --- | --- |
| 일반 몬스터 | 15% | 1 |
| 정예 몬스터 | 8% | 2 |
| 보스 | 100% (1회 한정, 등급 3 고정) | 3 |

- 약한 몬스터가 더 잘 나오는 구조라 보관함이 약한 그림자로 쌓이게 된다. 이것이 분해의 동기다. **[확정]**
- 추출 확률 보정(룬 `이른`, `우르드` 등)은 Phase 1 이후에 같은 테이블에 가산한다. 지금부터 `extractChanceBonus` 슬롯을 비워 둔다.

### 그림자 스탯 **[가정]**

```
hp  = 원본HP  × 0.6 × (1 + 0.08 × (level - 1))
atk = 원본ATK × 0.6 × (1 + 0.08 × (level - 1))
```

- 원본보다 약하게 시작하고, 강화로 성장시킨다. 계수 0.6은 "그림자 5마리가 플레이어와 비슷한 전투력"을 목표로 한 초기값이다.

### 분해 수익 **[가정]**

| 그림자 등급 | 정수 |
| --- | --- |
| 1 | 1 |
| 2 | 4 |
| 3 | 분해 불가 |

강화 비용: 레벨 n → n+1 에 정수 `n`개. (레벨 5까지 총 10개)

### 서버 상수 (`StatCaps` 테이블에 모은다)

```lua
ShadowConfig = {
  deployBase = 5,         -- Phase 0은 스킬 트리·장비 보너스 없음, 5 고정
  hardCap = 8,            -- 룬 시스템 도입 후에도 넘지 않는 절대 상한
  extractChance = { [1] = 0.15, [2] = 0.08 },
  statMultiplier = 0.6,
  levelGrowth = 0.08,
  respawnDelaySec = 10,   -- 사망한 그림자의 재소환 대기
  disassembleYield = { [1] = 1, [2] = 4 },
}
```

## 5. 엔티티·컴포넌트 구조

### 맵에 배치하는 것 (사용자가 메이커에서 구성)

| 엔티티 | 역할 | 부착 컴포넌트 |
| --- | --- | --- |
| 훈련장 맵 | 몬스터를 상대할 공간 | — |
| 몬스터 스포너 (일반/정예) | 일정 수를 유지하며 몬스터 생성 | `MonsterSpawner` |
| 보스 1종 | 보스 그림자 추출 검증용 | `ExtractTarget` |
| 분해 제단 NPC | 분해·강화 UI 호출 | `ShadowAltar` |
| `ShadowSystem` 관리 엔티티 | 월드 단위 서버 로직 | `ShadowSystem` |

### 스크립트(컴포넌트) 구성

| 컴포넌트 | 위치 | 실행 | 책임 |
| --- | --- | --- | --- |
| `ShadowConfig` (데이터 모듈) | 공통 | 서버 | 수치 테이블. 로직 없음 |
| `ShadowSystem` | 관리 엔티티 | ServerOnly | 처치 이벤트 수신, 추출 판정, ShadowData 생성, 소환 슬롯 검증 |
| `ShadowOwner` | 플레이어 엔티티 | ServerOnly + `@Sync` | 보관함 목록 보관, 소환 중 목록, 정수 수량 |
| `ShadowUnit` | 소환된 그림자 엔티티 | ServerOnly | 개체 스탯, 추적·공격 AI 틱, 사망 처리 |
| `ShadowUI` | 클라이언트 UI | ClientOnly | 보관함 목록·소환·분해 UI, 입력 → 서버 요청 |
| `ShadowAltar` | 제단 NPC | ServerOnly + ClientOnly | 분해·강화 요청 접수 |

**[확인 필요]** 클라이언트 → 서버 요청 전달 방식 (`ShadowUI` → `ShadowOwner`). 이게 구현의 첫 관문이다.

## 6. 데이터 흐름

### 추출
1. 서버: 몬스터 처치 이벤트 수신 **[확인 필요: 이벤트 이름]**
2. `ShadowSystem`이 원본 등급으로 확률 판정 (서버 난수 `_UtilLogic:RandomDouble()`)
3. 성공 시 `ShadowData` 생성 → 처치자의 `ShadowOwner` 보관함에 추가
4. 클라이언트로 알림 + 보관함 변경 반영 (`@Sync` 또는 이벤트)
5. 연출: 시체에서 혼이 플레이어에게 빨려드는 이펙트 (클라이언트 전용)

### 소환
1. 클라이언트: 보관함 UI에서 그림자 선택 → 서버 요청
2. 서버 검증: 소환 중 수 < `deployBase`, `respawnReadyAt` 경과, 해당 그림자가 소환 중 아님, 요청자 소유 확인
3. `_SpawnService:SpawnByModelId`로 그림자 엔티티 생성 → `ShadowUnit` 초기화 (소유자, 스탯)
4. `deployed = true`

### 전투
- `ShadowUnit` 서버 AI: 일정 주기(0.3~0.5초)로 가장 가까운 적 탐색 → 추적 → 공격
- 틱 주기를 `OnUpdate` 매 프레임이 아니라 타이머로 둔다. **[확정]** 소환수 32마리 상황의 서버 부하 대비
- 소유자와 일정 거리 이상 벌어지면 텔레포트 복귀 (끼임 방지)
- 사망: 엔티티 `Destroy`, `deployed = false`, `respawnReadyAt = now + respawnDelaySec`

### 분해
1. 보관함에서 소환 중이 아닌 그림자 선택 → 서버 요청
2. 서버: 소유자 확인, 분해 가능 등급 확인 → `ShadowData` 삭제, 정수 증가
3. 정수 수량은 `@Sync`로 클라이언트에 표시

### 저장
- 접속 종료 시 보관함·정수를 저장하고 접속 시 복원 **[확인 필요: 유저별 저장 API]**
- Phase 0 초기에는 **저장 없이** 세션 단위로 시작해도 된다. 재미 검증에는 영속성이 필요 없다. 저장은 루프가 확정된 뒤에 붙인다. **[확정]**

## 7. 서버 부하 가드레일

| 항목 | 기준 | 이유 |
| --- | --- | --- |
| 소환수 동시 수 | 플레이어당 5 (절대 8) | 엔티티 수 = AI 틱 수 |
| AI 탐색 주기 | 0.3~0.5초 | 매 프레임 탐색 금지 |
| 적 탐색 방식 | 충돌 시뮬레이터 질의 또는 범위 캐시 | 전 엔티티 순회 금지 **[확인 필요: 범위 질의 API]** |
| 추출 연출 | 클라이언트 전용 | 서버 엔티티 생성 없음 |
| 보관함 | 데이터만 보관, 엔티티 아님 | "무제한 보유"를 가능하게 하는 핵심 |

보관함의 그림자는 **엔티티가 아니라 데이터 행**이다. 소환했을 때만 엔티티가 된다. 이 구분 덕분에 보유 수를 무제한으로 둬도 서버 부하가 늘지 않는다. **[확정]**

## 8. 구현 순서

| 단계 | 작업 | 검증 |
| --- | --- | --- |
| 0-1 | 메이커 기능 확인: 처치 이벤트, 클라→서버 호출, 몬스터 컴포넌트 | 사용자가 확인해 알려줌 |
| 0-2 | `ShadowConfig`, `ShadowOwner` (메모리 상 보관함) | 로그로 보관함 변화 확인 |
| 0-3 | 추출 판정 + 알림 | 몬스터 처치 시 로그·UI 알림 |
| 0-4 | 소환·회수 + `ShadowUnit` 추적 AI | 5마리 소환해 전투 확인 |
| 0-5 | 보관함 UI | 목록·선택·소환 |
| 0-6 | 분해·강화 + 제단 | 정수 증감 |
| 0-7 | 부하 확인: 플레이어 1명 × 5마리 → 여러 명 | 서버 프레임·틱 지연 관찰 |
| 0-8 | **재미 판정**: 1장 성공 기준 점검 | 사용자 플레이 소감 |

0-1은 코드가 아니라 **조사**다. 사용자가 메이커를 설치한 직후 가장 먼저 같이 확인한다.

## 9. 열린 질문

- [ ] 소환수에 직접 명령(대상 지정 공격)이 필요한가 — 0-8에서 판정
- [ ] 추출 15%가 체감상 적절한가 — 일반 몹 7마리당 1마리 꼴
- [ ] 소환 슬롯 5개 중 몇 마리가 "의미 있는 선택"이 되는가 (전부 같은 몹이면 지루함)
- [ ] 그림자에 개성(원본 몬스터별 고유 스킬)을 Phase 0에 넣을지 — 재미 판정이 약하면 여기부터 추가

### 설계 반영
- 추출 판정은 `DeadEvent` 수신 시점에 하되, 처치자는 `HitEvent`로 추적한 마지막 공격자로 정한다. 그림자가 막타를 친 경우 그 그림자의 소유자를 처치자로 본다.
- 그림자 AI는 `AIChaseComponent.SetTarget` 위에 타이머 틱으로 대상만 갱신하는 방식을 먼저 시도한다. 직접 이동 구현은 그게 안 맞을 때만 한다.

## 11. 0-2 구현 결과 (2026-10-06, 메이커 실행 확인)

| 스크립트 | 종류 | 역할 |
| --- | --- | --- |
| `RootDesk/MyDesk/Shadow/ShadowConfig.mlua` | `@Logic` | 수치 테이블 (`_ShadowConfig`) |
| `RootDesk/MyDesk/Shadow/ShadowOwner.mlua` | `@Component` | 플레이어별 보관함·정수. 추가/분해/강화/소환 가능 판정 |
| `RootDesk/MyDesk/Shadow/ShadowSystem.mlua` | `@Logic` | 입장한 플레이어에게 `ShadowOwner` 부착. 0-3 추출 판정이 들어갈 자리 |

- **설계 변경:** `ShadowSystem`을 관리 엔티티의 컴포넌트가 아니라 `@Logic`으로 뒀다. 맵을 옮겨도 유지돼야 하는 전역 관리자이기 때문이다. `ShadowOwner`는 플레이어 모델 파일을 고치지 않고 `UserEnterEvent` 0.5초 뒤 `player:AddComponent(ShadowOwner)`로 붙인다.
- **실행 검증 (서버 로그):** 추출 3 → 분해 2 → 강화 2 후 보관 1, 정수 2로 기대값과 일치 → `PASS`. 자가 테스트는 `ShadowSystem.RunSelfTest`로 켜고 끈다(현재 false).
- **런타임으로 확인된 것:** 외부에서 만든 `.mlua`는 메이커 새로고침으로 `.codeblock`이 생성돼 인식된다. 런타임 `AddComponent(사용자 스크립트 타입)`이 동작한다.
- **남은 확인:** 런타임에 붙인 컴포넌트의 `@Sync` 값이 클라이언트에 전달되는지 (0-5 보관함 UI 전에 확인). 안 되면 플레이어 모델에 `ModelBuilder`로 부착한다.
  → 해결: `ShadowOwner`·`PlayerAttack`을 플레이어 모델에 직접 부착했고, `@Sync` 값이 HUD에 표시됨을 확인 (12장).

- `handler`는 예약어라 테이블 필드명으로 못 쓴다.
- 메이커 마우스 시뮬레이터는 엔진 UI 버튼을 누르지 못한다 → 버튼 검증은 핸들러가 부르는 함수를 클라이언트에서 직접 호출.

## 14. 성장·아이템·월드 단계 메모 (2026-10-07)

메이커에서 확인한 MSW 함정:
- 같은 엔티티에 AttackComponent 계열 스크립트는 하나만 붙는다 (LWA-3048). 스킬 판정은 PlayerAttack:SkillAttack을 거친다.
- 메서드 인자로 Shape 타입을 넘길 수 없다 (LEA-4002). 중심·크기·각도 값으로 넘긴다.
- Logic의 OnInitialize에서 채운 table 속성이 비어 있을 수 있다. 첫 조회 때 만드는 지연 생성으로 바꿨다 (SkillData·ItemData·QuestData).
- 새 모델을 맵에 배치하면 refresh를 두 번 해야 런타임에 엔티티가 생긴다 (모델 등록 → 맵 재로드).
- 한글 문자열은 string.sub로 자르면 깨진다. UTF-8 글자 단위로 자른다 (GameHUD.Clip).
- UI 그룹 순서가 같으면 겹침 순서가 불안정하다. 창이 있는 GameHUD는 GroupOrder 5.
