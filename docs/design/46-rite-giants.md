### 0-2. 진단 다섯 줄

1. **지금 거인은 「큰 해골」 하나다.** 5기를 바치면 생명이 가장 튼튼한 해골 하나가 1.8배로 커지고(`SU:929-931`) 휩쓸기 · 도발만 한다(`SU:911-937`). 무리에 대검이 셋이든 방패가 셋이든 결과가 같아 **변이를 모을 이유가 거인에 이어지지 않는다.**
2. **숫자로는 「무리에 강하고 보스에 약한」 기술이다.** 같은 다섯의 평시 대비 무리 1.64배 · 보스 0.76배(부록 A-2 — 대상 수 가정 계산이라 실측 아님 · §10-4). 보스에게는 다섯이 그냥 싸우는 편이 낫다 — 5기를 쓸 이유가 「도발」 하나다.
3. **마법사는 거인 재료가 될 수 없다.** 의식은 해골 전사만 센다(`US:90` `LiveUnits(player, "skeleton")` · `SB:1062-1069`). 마법사 위주 빌드는 5기 단계를 아예 못 연다.
4. **규칙 구멍 둘.** ① 거인 몸이 변이 기록이면 편성 미리보기가 그 변이를 「서 있다」로 센다 — RB-OBS-03의 원인이 `US:786` 한 줄이다(§2-6). ② 거인이 서 있는데 5기 재사용이 돌아오면(시전 속도로 30초 → 20초 아래) `RiteBestStage`가 5를 골라 서버가 거절하고 **아무 단계도 안 나간다**(`SB:1077-1088` · `US:130-133`).
5. **그림 · 노출 위험은 실재한다.** 종마다 30장이면 150장(+기술 효과), 5기는 악몽부터라 노말 플레이어는 못 본다(`SB:1055-1060`). 다만 **그림 없이도 시작할 수 있다** — 변이 해골 프레임은 이미 26장씩 있어(`data/monster_frames.csv:294-` `form_skelform_*` · `form_mageform_*`) 지금처럼 1.8배로 키우면 종마다 다른 임시 거인이 바로 선다.

## 2. 거인을 정하는 규칙

### 2-1. 진단

- 결정 A는 「합쳐지는 다섯 중 다수」다. 그런데 **어떤 다섯이 합쳐지는지**가 정해져 있지 않으면 다수가 흔들린다. 지금 소모 순서는 「생명 비율 낮은 순」(`US:51`)이라, 다섯을 그 순서로 고르면 전투 중 생명이 바뀔 때마다 고리 예고가 「대검 거인 ↔ 방패 거인」으로 깜빡인다. → 결정 결과(§2-4 · §10-1): 참여 다섯은 생명이 아니라 **소환 순서**로 정한다.
- 변이 정원은 노드 랭크(최대 3)다(`US:659-665` · `csv:6-8`). 그래서 **한 변이 5기는 원리상 불가능**하고(고르지 않은 안 B가 지금 규칙으로는 성립하지 않는다), 다섯 중 다수는 많아야 변이 3기다.
- 변이를 모두 찍은 후반(정원 10 · 방패 3 · 대검 3 · 쌍칼 3 · 일반 1)은 **세 변이가 3:3:3 동률**이다(`US:652-657` 채우는 순서 · `cfg:111`). 동률 규칙이 곧 후반 거인을 정한다.

**몸(host) — 지금 「가장 튼튼한 해골이 거인」 규칙과의 관계**: 지금 규칙(`US:134` 「생명 비율이 가장 높은 하나」)은 **다섯을 고르는 데에는 더 이상 쓰지 않고, 정해진 다섯 안에서 몸 하나를 고르는 데만** 남긴다. 몸 = 참여 다섯 가운데 **이긴 종류**의 해골 중 생명 비율이 가장 높은 것(같으면 목록 앞). 몸 고르기는 거인 종류 · 생명 · 공격 합(다섯 합) · 예고 문구 어느 것도 바꾸지 않고 거인이 서는 자리와 「몸이던 기록」만 정하므로, 서버 전용 값(생명 비율)을 써도 예고와 어긋나지 않는다. 몸의 변이 = 거인 종류라 편성 표시(§2-6)가 맞는다. 마법사 거인의 몸은 참여한 마법사 중 하나라 원소 = 그 마법사 원소(§3-2).

### 2-6. RB-OBS-03 정리 — 거인 몸과 합쳐진 넷의 변이

- **원인(확정)**: 편성 미리보기의 장기 편성 `SteadyRoster`는 거인 몸 기록을 씨앗으로 넣고(`US:777-779`), 매 반복 「서 있는 수」를 셀 때 **몸도 센다**(`US:786` `for _, r in ipairs(list) do now[r.form] = …`). 몸이 쌍칼(`s:twin!`)이면 쌍칼이 「1기 서 있다」로 잡혀 `FormHint`(`SB:753-755`)의 「뼈 거인이 서 있는 동안 0기」 조건이 거짓이 된다. 몸이 일반(`s:!`)이면 쌍칼이 0이라 경고가 뜬다 — 관찰과 정확히 같다. 오프라인 검사(`tests/quality/roster.lua:219-259`)는 몸이 방패인 경우만 봐서 통과했다.
- 합쳐진 넷은 목록에서 빠지고 수(`reserved`)만 남아 **변이 자리를 비운다**(`US:137-149`). 그래서 거인 동안 일으키면 넷과 같은 변이가 다시 서고, 갈라진 뒤 그 변이가 정원(랭크)보다 많아진다(총수는 `TrimVictims`가 맞추지만 변이 수는 아님).

| 안 | 내용 | 예상 | 위험 | 구현량 |
|---|---|---|---|---|
| **R1 거인 몫은 「자리는 쓰되 서 있지 않음」** | ① `SteadyRoster`의 서 있는 수에서 `giant` 기록을 뺀다(`US:786`) ② 합쳐진 넷도 변이를 담아 동기화(`EncodeRoster` `s:shield~` — `~` = 거인에 합쳐짐)하고, `PickForm`은 몸·넷의 변이를 **쓰는 자리**로 센다 ③ 경고 문구는 그대로 | 몸이 무엇이든 「거인 동안 0기」가 같은 규칙으로 뜬다 · 갈라진 뒤 변이 정원 초과가 사라진다 | `reserved` 수와 `~` 기록이 이중 — `reserved`는 `~` 수에서 계산하도록 하나로 | 0.5일 |
| R2 몸 변이를 비움 | 거인이 되면 몸 기록 `form`을 ""로(원래 값은 `giantForm`에) | 한 줄 | 거인 동안 같은 변이가 하나 더 서서 갈라진 뒤 정원 초과 · 넷 문제는 그대로 |
| R3 표시만 고침 | `FormHint`에서 몸 변이를 따로 빼고 계산 | 경고만 맞음 | 규칙(정원 초과)은 그대로 |

**추천: R1.** §2-4에서 몸을 이긴 종류 안에서 고르므로 몸의 변이 = 거인 종류라 표시도 자연스럽다(「거인 본체 1」 · `SB:787`). `PickForm` · `SlotPlan`(`SlotCount`)의 `reserved`는 `~` 기록 수에서 계산한다. 검사: `tests/quality/roster.lua`에 몸 = 쌍칼·대검·일반·마법사 4경우 + 넷의 변이 정원 초과 경우를 더한다.

분류 메모(코덱스 10-29 22:52): RB-OBS-03은 앞선 범위에서 맥락 관찰로 받은 것이다. 46은 이를 거인 설계에서 함께 고칠 「규칙 구멍」으로 다룰 뿐, **확정된 옛 버그로 다시 분류하거나 닫힌 F/I 검사를 다시 열지 않는다.**

### 2-7. 고르기 의사 코드 (Opus용 · `UndeadSystem.GiantPlan` · 결정 1·2 결과로 고쳐 씀)

```
GiantPlan(roster, banner)   -- roster: EncodeRoster 모양 { kind = "skeleton"|"mage", form, giant(!), merged(~), notReady(?) } · 오래된 순
                            -- banner: 깃발 종류 ("" = 안 고름) · 서버(시전 순간 자기 목록)와 클라이언트(UndeadRoster)가 같은 함수 · 같은 입력 모양 (§2-4 J1)
  pool = roster 가운데 kind가 skeleton/mage이고 giant·merged·notReady가 아닌 것 (순서 그대로)
  if #pool < 5 then return nil
  picks = pool[1..5]                                     -- ① 참여 다섯: 결과 종류 · 깃발 · 생명과 무관 (E1 소환 순서)
  key(r) = (r.kind == "mage") and "mage" or (r.form == "" and "basic" or r.form)   -- 마법사 변이 5종은 모두 mage
  counts = picks의 key별 수 { basic, shield, greatsword, twin, mage }              -- ② 5종 한 줄 투표
  top = counts 최댓값 · tied = top인 종류들 (GiantFallback 순서로 정렬)
  if #tied == 1 then type = tied[1]                      -- 분명한 최다는 깃발과 무관
  elseif banner ~= "" and banner가 tied 안 then type = banner   -- ③ 깃발은 동률 최다 안에서만
  else type = tied[1]                                    -- GiantFallback = shield, greatsword, twin, mage, basic (§10-2)
  return { type, picks(목록 위치), counts, tie = #tied > 1, bannerUsed = (#tied > 1 and type == banner) }

-- 서버만 (StartGiant): host = picks 가운데 key == type인 것 중 생명 비율 최대 (같으면 목록 앞)
--   → 종류 · 합계 · 예고에 영향 없음. 나머지 넷 = picks의 나머지 (종류 무관 · 합쳐짐 ~)
```

- 거인 종류 키: `basic` · `shield` · `greatsword` · `twin` · `mage` (일반 전사 = `basic`).
- 서버와 클라이언트는 `type` · `picks` · `counts`가 모두 같다 — 입력이 같은 순서 · 같은 거르기이고 생명 비율을 쓰지 않으므로(검사로 고정 · 46-1). 처음 초안(P1)의 「클라이언트는 순서만 다를 수 있다 · `type`과 `counts`는 같다」는 철회.
- 예시 표는 §10-1.

## 부록 A. 시뮬 · 계산 근거

스크립트는 저장소에 넣지 않았다(조정자 지시 · 재현은 아래 그대로). 모두 `tools/sim_balance.py`를 모듈로 불러 쓴다.

### A-1. 해골 1기 값

- `S.DONE["runs"] = 난이도 수`(악몽 1 · 지옥 2 — 퀘스트 스킬 포인트를 난이도마다 다시 줌 `sim_balance.py:185-186`) · `S.DIFF_NOW["d"] = 난이도` 뒤 `S.build("P60", L, 1, diff)`.
- 해골 공격 = `dps["해골"] × skeletonCooldown 1.1 ÷ n_sk`(`sim_balance.py:279-284` 역산) · 해골 생명 = `sk_hp` · 마법사 공격 = `dps["마법사"] × 1.6 ÷ n_mg` · 마법사 생명 = 해골 생명 × 25/40(`cfg:105` · `cfg:77` — 스킬 레벨 % 차이 무시, 추정).
- 일반 몬스터 초당 피해 = `monsters.csv` 등급 1 전부를 `S.mon_stats(id, ml, 1)`로 그 레벨·난이도에서 계산한 `dmg ÷ atkIntervalSec`의 중앙값(statMul 1 · 정예·오오라 없음).

### A-2. 거인 초당 피해 · 버팀

- 대상 수 기대값(무리 · 추정): 반경 0.6 → 1.2 · 0.9 → 1.4 · 1.0 → 1.5 · 1.4 → 2.0 · 1.6 → 2.3 · 1.8 → 2.6 · 2.0 → 2.8 · 2.2 → 3.0 · 2.4 → 3.3 · 직선 6칸 → 3.0 · 단일 → 1. 보스 = 모두 1.
- 다섯 평시 = 5 × (A/5) ÷ 1.1초 × 1.2(반경 0.6) — 변이 효과(대검 반경·쌍칼 속도) 무시.
- 거인 = 기본 공격 배율 ÷ 간격 × 대상 수 + Σ 스킬 배율 ÷ 쿨 × 대상 수(쿨마다 썼다고 가정 · 스킬 2는 명령/보험으로 쿨마다 쓴다는 상한).
- 쌍칼 돌진 = 도착 ×2.0(단일) + 길 위 ×1.0(반경 1.4 대상 수). 마법사 자리 폭발 ×0.3은 반경 1.0 대상 수 − 1.
- 버팀 = 생명 배율 × H ÷ (1 − 받는 피해 감소) ÷ (공격하는 일반 몬스터 수 × 1마리 초당 피해). 방어·저항·재생(`SU:459-470`)·뼈 성찬 무시.
- **한계(결정 4 결과 · §10-4)**: 대상 수 기대값은 추정 · 스킬 2를 쿨마다 썼다는 상한(결정 3으로 무명령 자동이 빠져 실제는 명령 횟수만큼) · 변이 효과 생략 · `RiteRankMul`(랭크당 +3% 제안) 미포함. 종별 특기 · 약점 비교용 계산이지 실제 DPS나 재미의 증명이 아니다.

### A-3. 끝 레벨 확인

- `S.build`를 감싸 `diff ≥ 1`일 때만 `total × (1 + N/100)` → `S.chain("P60", None)`(노말 → 악몽 → 지옥 레벨·경험치 이어받기 `sim_balance.py:563-575`).
- 기준선은 `python3 tools/sim_balance.py --rite-check`의 기준과 같다(171분 17초 Lv41 · 135분 34초 Lv68 · 136분 00초 Lv90 — 10-29 밤 실행).
- 끝 레벨이 그대로인 까닭은 43 §5와 같다: 경험치는 퀘스트 경로와 처치 수로 정해지고 화력은 시간만 줄인다.
- 그래서 「끝 레벨 불변」은 이 경험치 경로 모델의 결과일 뿐, 거인이 안전하거나 재미있다는 검증이 아니다(§10-4). 빌드 +N%도 A-2 한계와 사용률 50% 가정을 그대로 진다.
